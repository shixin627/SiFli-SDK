# ADR-0021 — Tap 偵測用 FSR 真值資料重建:arming 特徵換相對門檻、stage-2 模型重訓 + 信心門檻

- **Status**: accepted (2026-08-28)
- **Agent**: Claude,離線量測驅動;真機 E2E 待 founder
- **Trigger**: founder 問「`paper_progam` 那份滑鼠空中按放的資料能不能拿來改手錶的 tap 判斷」。
  答案是可以,而且不是「相似資料」——那份 CSV 的 `ax,ay,az` **逐位元就是手錶 stage-2
  模型吃的 ch0-2**(韌體 `commu_send_linear_acce_buffer` 送 linear accel、手機
  `GsensorSample.parseFrame` 乘回 9.8/8192),外加一路手錶沒有的**指尖 FSR 按壓真值**。

## 診斷(離線複刻,不是推測)

`mouse3/work/watch_tap/` 逐行複刻 `waveform_capture_process()` +
`gesture_event_capture_hcpu()`,並把韌體 C 陣列裡的真模型抽成 `.tflite` 一起跑。
資料:`data3/mouse` **31 檔 / 153.4 分鐘 / 8 人 / 2445 個按壓**(774 個標為 tap)。

現行管線在這份資料上:**stage-1 recall 0.400、system recall 0.367、誤報 3.66 次/分**。

瓶頸不在模型,在 arming:

1. 按壓當下 `difference_accel`(=`|Δ‖a‖|`)峰值的**中位數是 0.29 m/s²**,
   而門檻地板是 **0.3** —— 門檻正好壓在分布中位數上,零餘裕。
2. 漏掉的 1467 個按壓裡 **1432 個(97.6%)是「特徵從未超過門檻」**,狀態機只吃掉 3.6%。
3. 因此 recall 完全隨「這個人敲多用力」擺盪:**每人 0.12(willson)~0.61(jack)**。
4. 把整段 accel 乘 1.5/2/3 倍重跑,現行設定 recall 0.400→0.651→0.725→0.762,
   窗率同步 20→53/分 —— 它並沒有變好,只是沿著同一條 ROC 滑動。

## 決策

### 1. arming 特徵:`|Δ‖a‖|` → `‖Δ²a‖`

先取模再差分會丟掉方向,而敲擊最鮮明的特徵正是加速度方向在兩三個樣本內翻轉
(數學上恆有 `|Δ‖a‖| ≤ ‖Δa‖`,舊特徵是新特徵的下界)。同一個「每分鐘切幾個視窗」
預算下的 recall:

| 特徵 | 20 窗/分 | 30 窗/分 |
|---|---|---|
| `\|Δ‖a‖\|`(舊) | 0.389 | 0.569 |
| `‖Δa‖` | 0.482 | 0.637 |
| **`‖Δ²a‖`(新)** | **0.562** | **0.687** |

成本:每樣本 6 減 3 乘 2 加 1 平方根。

### 2. 門檻:絕對地板 0.3 → 相對門檻(地板 0.10、K 5→4)

地板降到 0.10 後幾乎不再作用,判定變成「相對於當下雜訊底的比值」,因此
**對訊號強度免疫**:accel ×1/×1.5/×2/×3 重跑全都是 recall 0.782 / 48 窗/分。
這一點決定了結論能不能外推 —— 就算錶上真正的捏指比這份資料用力,新設定照樣成立。

吃「背景中位數」的兩個常數同步照 ×1.9 換算(新舊特徵的背景中位數 0.054 vs 0.028):
`GESTURE_CONTEXT_WALK_MEDIAN` 0.03→0.058、median veto 0.25→0.48(改成具名常數
`GESTURE_MEDIAN_VETO`)。`RELEASE_START_THRESHOLD` 照等窗率係數 1.0→1.35。

### 3. stage-2:模型重訓、PPG 拿掉、加信心門檻

* **PPG 拿掉**(`kChannelReleaseNumber` 4→3):留一人交叉驗證下 PPG 是**負貢獻**
  (同架構 3 通道 0.461 > 4 通道 0.442;大架構 0.599 > 0.508),與論文 §5.6b
  的獨立消融一致;而且手錶的 PPG 還有已知的「兩值交替」缺陷。
* **模型**:843 參數 → 1263 參數(Conv12×(5×3) → MaxPool2 → Conv12×(3×1) →
  MaxPool3 → Dense12 → Dense3),8404 B(既有的 `MAX_RELEASE_MODEL_SIZE` 10 KB
  不用動),約 12K MAC/次,arena 用不到 3 KB(上限 8 KB)。**再放大沒有用**:
  2131 參數 0.556 / 4539 參數 0.506 / 1263 參數 0.532(@≤1 誤報分,同一次跑),
  差距小於種子變異。
* **信心門檻 0.75**:舊版 `PredictGesture` 是**裸 argmax**,三類 softmax 最低
  0.34 就會贏 —— 等於「不確定」這個選項不存在,每個切出來的視窗都會被指派成
  tap 或 release。低於門檻回 `kUnknownGesture`(2)**不是 0** —— 0 是 release 類別。
  **門檻由 `data3/free` 主導,不是 mouse**:照 mouse 挑會選到 0.55,但那個門檻在
  free(自由活動、完全沒按)上是 3.48 誤報/分,比現行的 1.78 還糟。0.75 是
  「兩個資料集都不輸現行」的最低門檻。
  MSH `gtap thr <0..100>` 可即時調(刻意放在 `!kReleaseMode` 之外,因為
  dev/release 現在是同一塊板);`gtap golden` 用固定輸入驗模型有沒有裝對。

## 結果(同一份 153.4 分鐘、同一組 2445 個按壓真值)

新模型走**留一人交叉驗證**(測誰就不訓誰),現行模型對這份資料本來就是
zero-shot,兩者都沒看過測試那個人。

**先講變異**:同一組設定重跑會落在不同位置(第一次 0.599、重跑 0.469)。
出貨只放一顆模型,所以下面報的是 **5 個種子的平均 ± 標準差**。

| 誤報預算 | 新系統 recall | 最低 | 最高 |
|---|---|---|---|
| ≤0.5 /分 | 0.390 ± 0.086 | 0.238 | 0.487 |
| ≤1.0 /分 | 0.505 ± 0.050 | 0.417 | 0.567 |
| ≤2.0 /分 | 0.587 ± 0.025 | 0.541 | 0.617 |
| **≤3.66 /分**(現行系統的誤報率) | **0.633 ± 0.014** | 0.608 | 0.650 |

變異集中在高門檻端(softmax 已飽和,P(tap) 會輸出 1.000000,排序由隨機初始化
主導);低門檻端很穩,而那正是拿來跟現行系統比的地方。

### 出貨設定(門檻 0.75)—— 三個量測軸都不輸

| | 現行 | 新 |
|---|---|---|
| stage-1 recall | 0.400 | 0.782 |
| 視窗率 | 20.5 /分 | 48.0 /分 |
| **recall(2445 個按壓)** | **0.367** | **0.514** |
| **誤報(mouse 操作情境)** | **3.66 /分** | **0.77 /分** |
| **誤報(free 自由活動)** | **1.78 /分** | **1.70 /分** |

recall +40%、mouse 誤報 −79%、free 誤報持平。

若只比模型本身(固定誤報率下能拿到多少 recall,不管出貨怎麼取捨):在現行系統
自己的 3.66 誤報/分上,新管線是 **0.633 ± 0.014 vs 0.367**,相對 **+72%**。

## 已知邊界

1. **★ 純負樣本嚴重不足,而那正是真機最在意的情境。** 訓練與評估用的負樣本
   都是「操作滑鼠時的手部移動」—— 很硬,但都是「正在按東西的人」。唯一的
   純負樣本 `data3/free`(自由活動、完全沒按)只有 **4.5 分鐘**,而且量到的結果
   **對新管線不利**:現行誤報 1.78/分(8 次)、新管線(門檻 0.55)2.89/分(13 次)。
   8 vs 13 在 4.5 分鐘上 Poisson 信賴區間完全重疊,統計上分不出來 —— 但這表示
   「誤報變少」這個結論**只在滑鼠操作情境下有證據**。出貨門檻因此改成用
   `tune_threshold_free.py`「兩個資料集都不得比現行差」來挑。
   **待補**:專門錄幾十分鐘的日常負樣本(走路、打字、通勤)。
2. **域差距**:資料的「按壓」是指尖壓感測墊,不是錶面上的捏指。決策 2 的強度掃描
   說明 arming 不受影響,但 stage-2 的權重是在這個域學的。
3. **gyro 與 gravity 沒用上** —— 手機的 0x50 parser 把 byte 12..17 當 gyro 丟掉,
   實際上韌體塞的是 gravity,所以資料集兩路都缺。兩者手錶上都拿得到,是下一個槓桿。
4. 狀態機還有約 5 個百分點可撈(新 arming 下漏掉的 532 個裡有 23% 是 realign /
   arm timeout 吃掉的),這輪沒動狀態機。

## 真機驗證怎麼做的(下次要重跑看這裡)

* **刷機**:`uart_download.bat` 之前必須先把 COM11 的 **DTR 拉高、RTS 放低** ~150 ms
  (CH342 的控制線接到 RESET/BOOT)。少了這步會固定卡在
  `EnterDebugMode success` → `WriteMem error: 0xf000edf0`(寫 DHCSR 停不了核心),
  試 15 次都一樣。COM11 燒錄、COM12 看 log。
* **dev build 在 VER_29 板子上不能用 `set_build_mode.py dev`** —— 它會把
  `CUSTOMER_BOARD_VER` 翻成 BOARD_VER_28 並把 LCPU 的 GH3018/BMI270 電源腳位
  設成 161/118,但開發錶與發布錶現在是同一塊 VER_29 板。正確的最小 delta 只有三個:
  `bsp_board.h` 的 `kReleaseMode` 1→0、`hcpu/proj.conf` 的 `RT_USING_FINSH=y`、
  `BSP_USING_VIRTUAL_CONSOLE` 關閉。**`ULOG_OUTPUT_LVL_W=y` 必須留著**,拿掉會撞
  image 上限(`L6406E: No space in execution regions`)——但留著會讓 `LOG_I` 在編譯期
  消失,所以 `CUT`/`GST` 兩行診斷改用 `rt_kprintf`(仍在 `#if !kReleaseMode` 內,
  release 不受影響)。
* **測 tap 前要先 `gcap both`** —— 預設 `motion_control_lock=1` 時只跑 RELEASE 抽取器。
* **手錶必須真的戴著**,否則 stage-2 一律 `GST drop=not-worn`,配戴偵測沒有 MSH 可假造。

實測結果(dev build,founder 戴錶):

| 階段 | 視窗 | 判成 TAP |
|---|---|---|
| 捏指 | 13 | **12** |
| 甩手(完全沒捏) | 38 | 5(擋掉 87%) |

`gtap golden` 回 **MATCH**(真機 TFLM `104/77/818` = PC 端 TFLite),證明模型正確寫入、
3 通道接線正確、離線數字對得上這支錶。相對門檻的機制也在 log 裡直接看到:
捏指段 `med=1~5 → thr=10~20`,甩手段 `med=5~33 → thr=22~132`(自己抬到 13 倍),
所以甩手的 `pk=350` 被擋、捏指的 `pk=47` 通過。

**注意**:`CUT`/`GST` 走 `rt_kprintf` 沒有時間戳,而周圍唯一的 ulog 錨點是每 ~100 秒
一筆,所以**算不出「每分鐘幾次誤報」**,上面只能報比例。下輪在 CUT 行加個 tick 就能解。
